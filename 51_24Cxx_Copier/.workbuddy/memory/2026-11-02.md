## 上位机芯片下拉框容量显示修复（avalonia_upper）

用户反馈"下拉框对容量的参数有问题"。核查：`ChipCatalog` 里 `Bits` 数值全部正确
（24C01=1024 … 24C1024=1048576 位），错误在 `ChipModel.BitsText` 的换算：

- 原：`Bits >= 1024 ? $"{Bits/1024} Mbit ({Bits} Kbit)" : $"{Bits} Kbit"`
  → 1024 位就判成 Mbit，且括号里把位当 Kbit 打印。
  实际渲染：24C01 = "1 Mbit (1024 Kbit)"，24C64 = "64 Mbit (65536 Kbit)"（应为 1 Kbit / 64 Kbit）。
- 改：`Bits >= 1024*1024 ? $"{Bits/(1024*1024)} Mbit" : $"{Bits/1024} Kbit"`，
  并补注释说明阈值与整除前提（24Cxx 全是 2 的幂）。
- 同时修正 `ChipCatalog` 中 24C1024 的 `AddressBytes` 3 → 2，Note 改为
  "2 字节字地址 + A16 作为器件地址 P0(bit1)"（查 AT24C1024 手册确认 A16 = 器件地址 bit1，
  与固件 `EE_1024_A16_MASK = 0x02` 一致）。

验证：`dotnet build --no-restore` 通过（0 error，14 个既有的 nullable 警告）。
注意：本机 `dotnet build` 带 restore 会报 NuGet "Value cannot be null (path1)"，需加 `--no-restore`。

## 实机问题修复：EDGE 报 R-ERR + TM1637 全黑

用户实测：`>ROUTER_0x50<` 回 R-S，`>EDGE_0x00FF<` 回 R-ERR（板上 0x50 是 24C64）；数码管全黑。

**原因 1（EDGE）**：上一版把"槽位地址=芯片型号"写死（沿用模拟器测试表 0x50=24C01，上限 0x7F）。
改法：`HW_24c64.c` 拆分 `EE_TYPES[11]`（型号库）与 `EE_SLOT_TYPE[8]`（槽位→型号），
默认 `EE_SLOT_CHIP_DEFAULT = EE_CHIP_24C64`（8 槽全 24C64）；EDGE 上限改为取所选型号的 max_addr。
副作用：与模拟器的设备表不再逐字节一致（已在 README 顶部说明）。

**原因 2（TM1637 全黑）**：位延时 `CFG_TM1637_DLY_US` 原为 2。用 C51 汇编数周期：
`Delay1us` = MOV+2×DJNZ+RET = 7 周期，加调用/循环开销约 0.65us/单元，
每 bit 有 3 次延时 → bit ≈ 3×2×0.65 = 3.9us ≈ 256kHz，超过 TM1637 的 250kHz 上限 → 整帧丢弃。
改为默认 5（≈102kHz）。另给 `>DISP_TEST<` 调试命令：先 `Board_TM1637PinsOk()`
（推挽输出 0 后读回，读回 1 说明引脚不受控）再全段点亮 0.2s，回 YES/R-ERR。

**关键硬件知识点**：STC8G1K 的 P5.4 上电默认是 RST，必须在 STC-ISP 勾选"复位脚用作 I/O 口"，
否则 P5.4 永远不能输出 → 数码管 CLK 不动 → 全黑。已写入 README 9.1。

**仍待用户确认**：数码管 CLK/DIO 实际引脚。原工程 `HW_24c64.h` 把 P5.4/P5.5 定义成两路 WP，
与 `TM1637.h` 的 CLK/DIO 冲突，当前固件取 TM1637=P5.4/P5.5、WP=P3.4/P3.5，属推测。

编译：`UV4 -r` 全量重建通过，data=62.0 xdata=152 code=5050，0 error 0 warning。

## 追加：I2C 读到全 0xFF 的分析 + `>I2C_TEST<`

用户加了个 SCL 指示灯（低电平亮），通讯时"没亮"，且读回数据全 0xFF。

**推理**：固件对每个 ACK 都判定，任何 NACK 都回 R-ERR。要"读出 256×0xFF 且不报错"，
必须器件地址/2 个地址字节/读地址全部被 ACK（SDA 拉低），同时 16×8 个数据位全读到 1（SDA 高）。
一条死线不可能同时满足 → 总线实际在跑，0xFF 更可能是**空白片**；但也可能是
"I2CRXD 复位值 0xFF + 读路径未真正移位"，用"写已知图样→读回"区分。

**SCL LED 不亮的可能**：① LED 接错网络（以为 SCL=P3.2，实际线在别处）；② LED 串在总线里/方向错；
③ 限流电阻太小把低电平抬高；④ 接的是 TM1637 的 CLK(P5.4) 而不是 I2C SCL。
已提醒用万用表测 SCL 平均电压来判定，并说明 I2C 需要上拉（4.7k~10k），不能有下拉。

**新增调试命令** `>I2C_TEST<`：只做 START+器件地址+等 ACK+STOP，不碰数据，YES/R-ERR。
实现：`HW_24c64.c` 的 `EE_Probe()`（内部用 `ee_sa()`，需前置声明）。

编译：data=62.0 xdata=152 code=5124，0 error 0 warning。

## 真因确认：STC8G1K08A 的 I2C_S 引脚表与通用 STC8G 不同

用户提供手册后查实（P_SW2 章节 3.1.2）：
- **STC8G1K08A / STC8G1K08-8Pin：I2C_S=00 → SCL=P3.2/SDA=P3.3；01 → P5.4/P5.5；10、11 为保留（无引脚）**
- 其它 STC8G（1K17A 等）：00→P1.5/P1.4，01→P2.5/P2.4，10→P7.7/P7.6，11→P3.2/P3.3

上一版按通用表把 `CFG_I2C_PIN_SEL` 设成 3，在 08A 上是保留值 → I2C 不驱动任何引脚。
这精确解释了全部症状：SCL 恒高（用户 LED 不亮）、I2CRXD 恒读 0xFF、ACK 位判成 0 所以不报错。

**修复**：board.h 增加 `CFG_MCU_IS_08A`，08A→`CFG_I2C_PIN_SEL=0`，其它→3；
总线恢复改用 `CFG_I2C_ON_P32_P33` 控制（两者都落在 P3.2/P3.3）。uvproj IROM 改 0x1FFF（8K）。
MCU 已换成 STC8G1K08A（8K Flash / 256B idata / 1K xdata），code=5119 仍装得下。

## TM1637 手册核对（纠正上一轮的错误结论）

TM1637 手册 AC/时序特性（测试条件 **VDD = 4.5~5.5V**）：
- Fmax **500kHz**（占空比 50%）；250kHz 只是"读按键"时的限制
- PWCLK ≥ 400ns、tSETUP/tHOLD ≥ 100ns、**tWAIT（CLK↑→CLK↓）≥ 1µs**
- **VIH = 0.7×VDD = 3.5V（5V 供电时）**

所以 5V 模块 + 3.3V MCU 必然全黑（3.3V 达不到 3.5V 门限）；
CFG=2 时 tWAIT≈1.3µs 只是"余量小"，并非超 250kHz。默认改 5（tWAIT≈3.3µs）属保守措施。
结论：数码管全黑优先查**供电电平**与接线，其次才是时序。

## "段码错乱"其实是时间叠加（C∪o = 6）

用户报 `dC50` 显示成 `d650`、写流程显示 `U650`。**不是段码表错**：
- 'C' = 0x39 = {a,d,e,f}，'o' = 0x5C = {c,d,e,g}，并集 = {a,c,d,e,f,g} = 0x7D = **'6'**
- 段码"置换错位"不可能让点亮的段**变多**（4 段→6 段），所以排除映射问题
- 真正原因：写流程每包 ~11ms（C 约 6ms / o 约 5ms），读流程每包 ~5.6ms
  （- / C / o 三态循环），切换 90~180Hz，人眼把相邻帧叠加 → 看到 6

修法：流程内只用一个不闪的码（`display.c` 的 s_pfx）：
- ST_WRITE_WAIT/CURR/OVER 全部 → `UC`（U=write, C=busy）
- ST_READ_WAIT/CURR/OVER 全部 → `dC`（d=download）
这样缓存判定使得 TM1637 在整个流程中只写一次，不闪也不叠加。

## 24C128 写成功、读整片报 R-ERR

现象：0x57 写 6814 字节（EDGE 0x1A9D）成功；读 16384 字节（EDGE 0x3FFF）回 R-ERR。

原因：固件不从上位机拿芯片型号，槽位型号表默认是 24C64（max 0x1FFF）。
6814 < 8192 所以写通过了，读整片才越过上限。

修复：`EE_SLOT_CHIP_DEFAULT` 24C64 → **24C1024**（语义 = "2 字节地址、不限容量"，max 0x1FFFF）。
依据：24C32~24C1024 片内地址都是 2 字节，且本协议每包 ≤16 字节、地址 16 对齐，
而器件页最小 32 字节 → 永不跨页，页大小差异对协议无影响。
例外：24C01/02/04/08/16 是 1 字节地址，必须在 `EE_SLOT_TYPE[8]` 里显式配置。

小结（这类"写入能成、读整片报错"的排查顺序）：先看 EDGE 是否超过槽位型号的 max_addr，
再怀疑总线和时序。

## 致命 bug：page 被 uint8_t 截断导致写流程死循环

现象：读 8KB 正常；写第一包就失败，报 "Packet @0x0 not acknowledged (got Error)"，
之后像卡死（只能复位）。用户描述为"中途取消后读写都报错"。

根因：`ee_dev_t.page` 是 `uint8_t`，而 24C1024 的页大小是 **256** → 被截成 **0**。
`EE_WriteBlock` 里 `chunk = page - off = 0` → `ee_write_page(len=0)` 只发地址不发数据却返回成功
→ `len -= 0` 永远不减 → **死循环**（每圈还等 5ms）。读流程不用 page，所以一直正常。
把这个类型改成默认值（上一轮为修 24C128 的 EDGE）后，所有写操作都踩中。

修复：
1. `page` 改 `uint16_t`；
2. 块写用 `uint16_t space` 计算，`chunk = (space > len) ? len : space`，并加 `chunk == 0 → return 0`；
3. `ee_write_page` 入口加 `len == 0 || len > CFG_PKT_BYTES → return 0` 防御。

教训：宽度类字段（页大小/容量）在 8 位机上别用 uint8_t；循环里"进度为 0"必须兜底。

编译：data=62.0 xdata=152 code=5165，0 error 0 warning。

## 写 0x50 成功、写 0x57 第一包 R-ERR 的定位（结论：槽位无器件）

日志：ROUTER_0x57/EDGE_0x1FFF/INT_W 都 R-S，然后包 0 只有一条 R-ERR，
上位机报 "Packet @0x0 not acknowledged (got Error)"。

判定链：
1. `CopierProtocolSession.QuietHandshake` 只隐藏 `RX-OK` 和 `R-S`，**R-ERR 永远打印**
   （`IsSuppressedFrame`）。所以"看不到 RX-OK + 一条 R-ERR" = 整包已收到、**写 EEPROM 失败**。
2. 同一份固件写 0x50 跑了 512 包全成功 → 驱动/时序/页拆分/写周期没问题。
3. 两次唯一差别是器件地址：0x50→0xA0、0x57→0xAE → 该地址没人 ACK（NACK）。
4. `cmd_router` 只校验 0x50~0x57 不探测器件，空槽位能一路过 ROUTER/EDGE/INT_W，
   到第一包才炸 → 看着像协议坏了。

日志里 `[OPT]`/`[DATA]` 顺序错乱是**日志线程不同**造成的假象：
service 的 `_log` 在 `ConfigureAwait(false)` 后从线程池调用，走 `Dispatcher.Post`（异步），
而 VM 的 `Log` 在 UI 线程同步执行 → VM 行会插到前面。不是协议乱序。

改动：
- 固件新增 `>SCAN<` → `>SCAN_[XX]<`，位掩码 bit0=0x50…bit7=0x57，一次看清哪些槽有片子
  （`EE_ScanMask()` 临时改 s_addr7/s_type 后恢复）。
- 上位机 `CopierProtocolSession.WritePacketExAsync` 返回 `PacketResult(Ack, RxOkSeen)`，
  `WriteAsync` 据此区分"EEPROM 写失败（无片/地址不对/WP 拉高）"和"没收到 RX-OK"，
  不再统一显示成 "not acknowledged"。

编译：固件 data=63.0 xdata=152 code=5309；上位机 0 error（14 个既有 nullable 警告）。
注意：上位机进程在运行时 exe 被锁，`dotnet build` 会 MSB3027；可用
`-p:BaseOutputPath=bin_verify\` 验证编译。

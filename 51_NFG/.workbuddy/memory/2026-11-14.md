# 2026-11-14

## JLX12864G-086 显示只有方块/花纹，无汉字 — 定位与修复

**现象**：屏幕能亮、能刷出图形，但"测试""我是傻鸟"全变成实心方块和规律变化的花纹。

**根因分析（按可能性排序）**
1. **P0 开漏口无上拉**（最可能）：原理图上 `ROM_SCK=P0.5`、`ROM_OUT=P0.6`，工程 `nfg.uvproj` 的 Device 是 **AT89C52**（P0 无内部上拉）。写 1 只是高阻，字库 SCK 抬不起来 → 读回全是悬空噪声 → 每格 16x16 变实心块 / 花纹。LCD 走 P2/P3（准双向，带上拉）所以正常。
2. **模块可能是 -PN 版（不带字库 IC）**：原理图符号 `HS12864G06BN` 把 1~4 脚标成 NC；PN 手册明确"不带字库 IC，不用字库时为空"。若买到 PN，软件无解。
3. **ROM_CS 冲突**：模块第 4 脚 ROM_CS 在板上接地，而代码把 `ROM_CS` 定义成 `P1^5`，P1.5 实际是 74HC165 的 DQ_SRCLK。

**代码改动**
- `Display/d12864.h`：`ROM_CS` 改成 `ROM_CS_ON_MCU` 编译开关 + `ROM_CS_LOW/HIGH` 空宏（默认 0，因硬件接地）；加 `GB16_ADDR()` / `ASCII8_ADDR()` 地址宏；声明 `show_glyph_block()` / `font_selftest()`。
- `Display/d12864.c`：所有 `ROM_CS=0/1` 换成宏；`rom_read_bytes()` 补上 CS 时序（原来完全没拉 CS，若 CS 由 MCU 控制就必然读 0xFF）；修正错误的引脚注释；新增 `font_selftest()`（第1页竖条纹测 LCD、第3~4页"测"点阵、第5~6页二次读取对比、第8页三个 8x8 状态块：全FF/全00/读取不稳定）。
- `main.c`：上电先跑 `font_selftest()` 4 秒，再进正常循环。
- 编译验证：`UV4 -b nfg.uvproj` → 0 Error，`code=6707 data=11.2`，仅剩既有的 L16 未调用告警。

**待用户确认**：模块是 PC 还是 PN 版；P0.5/P0.6 是否已有 10k 上拉（万用表量 ROM_SCK 空闲应为 ~5V）。

## 追加实测（16:11）

- **P0.5 实测 3.7V / 2.65V**（既非 5V 也非 0V，漂移）→ 确认**没有上拉**，SCK 的"高电平"是浮空借来的电平。
  3.7V ≈ 3.3V+0.4V，像是被模块上 3.3V 供电器件的 ESD 二极管钳住 → **反证字库 IC 大概率存在（-PC 版）**，PN 版这 4 脚是空焊盘，量不出 3.3V 钳位。
- 模块丝印：`JLX12864G-08602 ver4.0`（不是型号后缀，判断 PC/PN 要看 FPC 上有没有 8 脚字库芯片 / 1~4 脚是否有引线）。
- 现象更新：纯白色方块 + 不断刷新，像乱码 → 与"SCK 无有效边沿、字库随机输出"一致。

**结论**：硬件缺上拉是主因。修法：P0.5、P0.6 各加 10kΩ 上拉到 +5V（官方例程就是 5V 51 直驱，5V 安全）。
备选：把字库 SCK/SO 挪到准双向口（P1.6/P1.7 或 P2.x），软件只改两行 sbit。

**自检改造（v2）**：`font_selftest()` 返回 0/1；故障时画整屏图案并**停在屏上**（main 里死循环）：
大棋盘=全0xFF、横色带=全0x00、45°斜纹=两次读不一致、真汉字=正常。
刻意用"结构图案"而非黑白，避免正显/负显判断错误。
- 编译：0 Error，`code=6507 data=11.2 xdata=181`。

**另外发现**：原理图 LEDA 由 P3.4 直接供电（背光 24~60mA），远超 IO 能力，可能造成掉压/复位（"不断刷新"的另一嫌疑）。

## 更正（16:15）：P0.5/P0.6 其实有 10k 上拉

用户反馈 PCB 上本来就焊了 P0.5 / P0.6 的 10k 上拉，且 P0.5 的 3.7V/2.65V 是用万用表在程序运行时量的。

**结论修正**：万用表测翻转中的时钟线 = 读平均值，2.5~3.7V 完全无法区分"有上拉"和"没上拉"。我此前"缺上拉"的推断**作废**。

**正确的电平验证法**（已写进固件）：
- `level_window()`：上电前 3 秒把 ROM_SCK 强制拉高 + 整屏刷黑（此时量应为 5.00V）；后 3 秒拉低 + 整屏刷白（应为 0.00V）。屏色即状态指示。
- 或者断电直接量 P0.5 对 +5V 的阻值，应为 10k。

**自检 v3（不依赖人眼判断黑白）**：`font_selftest()` 把 7 项硬件判定编码成 8 个 16×16 方块（实心=1/空心=0），从左到右 bit7..bit0：
bit7 SCK 能拉高 / bit6 SCK 能拉低 / bit5 非全FF / bit4 非全00 / bit3 两次读一致 / bit2 换地址数据会变 / bit1 有非空内容 / bit0 控制位恒 1。
全实心时直接显示"测试"+FONT OK。
- 编译：0 Error，`code=6824 data=11.2 xdata=188`（AT89C52 只有 8K Flash，余量约 1.3K，后续加功能要留意）。

**新的头号嫌疑**：模块第 2 脚 ROM_OUT 与第 3 脚 ROM_SCK 接反（相邻脚，极易焊错）。
表现正是：P0.5 上出现推挽对驱的中间电平（3.7/2.65V 飘）、读回全是垃圾。

## 内置 ASCII 字库（16:20）

用户确认图形显示正常，问"不用字库 IC 只显示英文是否可以"。答案：可以，走内置字模。

**实现**
- `tools/gen_ascii_font.py`：5x7 ASCII 点阵生成器（手工逐格设计，95 个可打印字符，往返校验 0 错），输出 C 数组 + 字符画预览。
- `Display/ascii5x7.h`：`uchar code ascii5x7[475]`，列存、bit0=顶行 —— 与 LCD 显存格式一致，写入时无需任何位变换。
- `Display/d12864.c` 新增：
  - `lcd_text(page,col,s)`：5x7，每字 6 列，21 字/行 × 8 行
  - `lcd_text_2x(page,col,s)`：2 倍放大 10x14，每字 11 列，11 字/行 × 4 行
- 开关 `USE_FONT_ROM` 移到 `Display/d12864.h`（0=只用内置字库，1=走字库 IC）。`d12864.c` 里整段字库 IC 代码用 `#if USE_FONT_ROM` 包住。

**关键教训：Flash 容量**
第一次编译 `code=8369`，**超过 AT89C52 的 8K**（只是宏包 main.c 不够，d12864.c 里的字库代码仍被链接）。把整段字库代码用 `#if` 排出编译后 → `code=4580`，余 3.6K。
→ 结论：8K 机器上"字库 IC + 内置 ASCII"二者只能选一，汉字 16x16 约 32B/字，全塞满也就 100 来个字。

**验证手段（可复用）**：用 Python 复刻 `lcd_text/lcd_text_2x` 的写显存逻辑，在 PC 上渲染 128x64 位图核对排版，再烧片。

**汉字三条路**：换 -PC 模块 / 自建 16x16 字模数组 / 外挂 SPI Flash。

## 阶段性结论（16:27）

英文显示完全正常 → 证明 LCD 侧（初始化、模拟 SPI、页/列映射、显存写入）**全部正确**，独独 MCU→字库 IC 这一段断。
"通讯不上"仍是四种可能，未定论：① 模块是 -PN 无字库 IC ② 接线错(SCK/SO 反、CS 悬空、虚焊) ③ 字库 IC 没供电 ④ 片选/时序。
判定法：二极管档黑笔接 GND、红笔点模块 1/2/3 脚；有 0.4~0.7V 体二极管压降=焊着芯片，OL=空焊盘。
自建字模容量：16x16 汉字 32B/字，当前 code=4580，装 ~100 字（3.2KB）刚好 7.8K，150 字就超。

## 确诊：ROM_CS 被接地（16:31）

用户给出 PCB 照片 + 四张原理图，结论修正如下。

**硬件其实是好的**
- 模块实物 `JLX12864G-08602 Ver4.0`，PCB 上有 8 脚 U1 丝印 `25Q80` = 1Mbit SPI Flash = 字库本体。**模块是带字库版本，不是 -PN**。
- P0.5→ROM_SCK 有 R4 5.1k 上拉；P0.6→ROM_OUT 有 R2 5.1k 上拉。接反/无上拉均排除。
- P0.0~P0.3 按键、P0.4 DA 由 RN1 10k 排阻上拉；P3.2/P3.3 也有。

**真凶：模块第 4 脚 ROM_CS 在原理图上直接接 GND，MCU 侧无连线**
（`d12864.h` 里 P1.5 是 74HC165 的 DQ_SRCLK，从来就不是 CS）
→ 25 系列 Flash 每条命令必须 CS# 出现高→低再回高；恒低时芯片一直停在"顺序读"，
上电后只有第一条 0x03 有机会被识别，之后的 0x03+24 位地址全被当时钟吃掉，
读回的是地址计数器继续往下的数据 → 每次不同 → 花纹/方块。与观察完全吻合。

**修复方案（待用户实施）**
1. 割断模块第 4 脚到 GND 的走线
2. 飞线到 **P0.7**（唯一空脚，pin 32）
3. P0.7 加 10k 上拉到 +5V（开漏）
4. 代码 `ROM_CS_ON_MCU` 改 1（已把默认引脚改成 P0^7，默认值仍为 0，防止未割线时灌电流烧 IO）

**代码结构调整**
- 新增 `USE_ASCII_FONT` 开关，与 `USE_FONT_ROM` 互斥，同时为 1 时 `#error`。
- 实测容量：ASCII 模式 `code=4580`；汉字模式 `code=6824`，都在 8K 内。

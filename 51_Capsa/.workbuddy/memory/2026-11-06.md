## 固件总线拓扑纠正：PCF8574 在 IIC2（0x20），IIC1 只挂 8 片 24Cxx

用户澄清此前接线描述搞混了，真实拓扑是：

- **IIC1**（P3.2/P3.3，硬件 I2C，`I2C_S=11`）：**仅** 8 片 24Cxx（0x50~0x57），纯存储器数据总线，不含任何控制/显示器件。
- **IIC2**（P5.4/P5.5，软件 I2C）：**显示 + 写保护控制 + 属性存储**三件事共用 —— SSD1315(0x3C) / PCF8574T(0x20) / 24C02(0x51)。
- 三条 IIC2 地址互不冲突，单主顺序访问，不需要分时切换。

改动：

1. `hardware/pcf8574.c/.h`：去掉 `CFG_PCF8574_USE_HW` 分支，写死走 `I2C2_Write / I2C2_WriteRead`（`wn=0` 的重复 START 读法，PCF8574 无寄存器地址阶段）；删除 `i2c_hw.h` 依赖。
2. `system/board.h`：拓扑注释与 `ADDR_PCF8574` 标注改为 IIC2；删掉并不存在的 `CFG_IIC2_USE_HW`「一键切硬件」说法（该开关从未实现，会误导）。
3. `user/main.c`：初始化顺序理顺 —— `EE_InitArray()`(IIC1) → `M24_Init()`(IIC2) → `UI_Init()` → 元数据 → `PCF_Init()` 再按掩码重发；删掉 `PCF_Init()` 之前那次多余的 `PCF_SetMask`。
4. `PCF_SetMask` 回读校验改正：PCF8574 是准双向口，写 1 的位只是弱上拉，24Cxx 的 WP 脚内部有下拉会把回读拉成 0 —— 只校验「被驱动为低」的位（`(~mask) & back == 0`），否则接真实负载后每次都误判失败。
5. 文档同步：`firmware/README.md`（拓扑表 + 目录说明 + 与模拟器差异段）、`CapsaSim/docs/COMMAND_REFERENCE.md`（§2.1 注、§9）。模拟器侧仍是 PCF8574 @ 0x58 on I2C2，仅地址不同，协议无影响（上位机从不直接寻址 PCF）。
6. 顺手清掉 `hardware/ee.c` 的 `uint8_t k` 未引用告警（之前增量编译漏掉，全量重建才暴露）。

编译结果：**0 Error / 0 Warning**，`data=93.1  xdata=811  code=16602`（Flash 17408，余 ~800B）。

## 致命 bug：固件忘了开 EA → 所有串口命令无响应

用户实测：发 `>TYPE-CAPASA<` 毫无返回，命令解析整块不工作（但 OLED 显示正常，容易误判成"协议不对"）。

根因：`main()` 从未执行 `EA = 1`。`Uart1_Init()` 里只有 `ES = 1`，注释还写着"总中断由 main 打开"，但 main 里没有 —— RI 置位后没人取走，下一字节覆盖 SBUF，帧永远组不起来。参考工程 `51_24Cxx_Copier/firmware/user/main.c` 里是明确有 `EA = 1` 的。

修复：
1. `main()` 开头 `EA = 0`（初始化期间关中断），`Uart1_Init()` 之后立刻 `EA = 1`（放在循环前太晚，会因为 24C02 读取 + OLED 初始化几十毫秒而漏掉上位机握手帧；ISR 只写协议缓冲，安全）。
2. `uart.c` 的 `AUXR &= 0xBF` 清的是 bit6(T0x12)，**T1x12 是 bit7** —— 改成 `AUXR &= 0x3F`（T0/T1 都 12T）。参考工程同一处注释也是错的，只是复位值恰好是 0 才没暴露。
3. 删掉 `Objects/copier*` 遗留产物（从 copier.uvproj 改造残留），避免烧错固件。

顺带核对（全部一致，无需改）：`>..<` 帧格式与 `CapsaProtocol.TryExtract` 匹配；`TYPE-CAPASA→[YES]`、`GET_!→INFO_` 9 字段、`UGS→[UG-n]`、`W_XX,XX` 逗号十六进制、`ROUTER_0xNN`/`ADDR_0xNNNN` 的 `parse_num` 支持 0x 前缀；应答令牌集合与上位机接受集合完全对齐。

记录两个判断点：
- TI 在 ISR 里不处理**不会**死锁：8051 规定 RETI 后至少执行一条指令才响应同级中断，`while(!TI); TI=0;` 会在第二次进入 ISR 后清掉 TI。参考工程同款写法且长期稳定，故保持查询发送不改环形缓冲。
- C51 的 `interrupt 4` 函数会被自动放到 `0023H` 向量（已用 `Listings/capsa.m51` 确认 `CODE 0023H 0003H ABSOLUTE` + `?PR?UART1_ISR?UART` 在 386BH 链接入）。

编译：0 Error / 0 Warning，`data=93.1 xdata=811 code=16606`。README 新增 §7 "排查：发命令完全没反应"（EA / ISP 的 IRC 必须 22.1184MHz / TX-RX 交叉 / 不要流控 / 帧必须以 `>` 开头 `<` 结尾）。

## 上位机握手失败 + OLED 全黑（15:40）

用户反馈：串口助手发 `>TYPE-CAPASA<` 能收到 `[YES]`，但上位机判"不是 Capsa 设备"，且 OLED 无任何内容。

**A. 上位机（Capsa）—— 探测太脆**
- 根因1：`CapsaProtocol.Open()` 打开端口后**立刻**写第一帧。CH340/CP2102 在端口刚打开时会清内部 FIFO，首帧经常整帧丢失；探测只发一次就判死 → 弹 "Not a Capasa device"。
- 根因2：`ProbeAsync` 把所有异常都吞成 false，包括 `UnauthorizedAccessException`（端口被串口助手占用）—— 用户明明能通，却只看到"不是设备"。实测时 COM5 确实被别的进程占着（我这边 open 也 PermissionError）。
- 修复：`Open()` 加 60ms 稳定期 + `DiscardIn/OutBuffer` + 新增 `ClearReceiveBuffer()`；`ProbeAsync` 重试 3 次（600ms/次，间隔 80ms）并区分端口占用；`ConnectAsync` 同样重试 3 次；`ISerialPortService` 新增 `LastProbeError`，TopBar 弹窗/状态栏直接显示真实原因。
- 实测证据：按新流程用 Python 直连 COM5（settle 60ms + discard）→ `[YES]\r\n`，hex `5b5945535d0d0a`，说明板子与协议都没问题，问题在探测时序/端口占用。

**B. 固件（OLED 全黑）—— 地址写死 + 引脚自检时机**
- 根因1：`OLED_Init` 只认 `ADDR_OLED=0x3C`，探测失败直接 return（连电荷泵都没开，必然全黑）。模块 SA0 接法不同，0x3C/0x3D 各占一半。
- 修复：`s_addr` 运行期可变，上电依次探测 0x3C→0x3D（各试 2 次），成功才初始化；新增 `bit OLED_Found`，UI 各入口 `if (!OLED_Found) return;` 短路，避免无屏时每次刷屏白等 I2C 失败。新增 `OLED_Addr()` 供诊断。
- 根因2：`Board_SwI2cPinsOk()` 原先在 `UI_Init()` **之后**调用，它把 P5.4/P5.5 推挽拉低再恢复，等价于在已初始化的屏上打一个假 START。已挪到 `UI_Init()` 之前。
- 顺带修 `UI_Capacity` 的 `char buf[17]`：满容量时 "63.9/64.0KB"+"100.0%"+"\0"=18 字节，会越界写一格 → 改 20。

**C. 新增固件扩展命令 `DIAG`**（上位机不依赖）
`>DIAG<` → `[DIAG_<OLED地址>_<PCF>_<24C02>_<阵列位图>]`，例 `[DIAG_3C_1_1_FF]`。
用来分线"屏黑/属性读不到"：三项全 0 = 整条 IIC2 没工作（优先查 P5.4 是否被 ISP 配成 nRST、上拉/接线）；仅 OLED=00 = 地址不符；阵列 00 = IIC1 无应答。

编译：固件 0 Error / 0 Warning，`data=96.3 xdata=812 code=16959`（Flash 17408，余 ~450B）；上位机 0 警告 0 错误。
待用户实测：烧新固件后发 `>DIAG<` 确认 IIC2 三器件应答；上位机重连（先关串口助手）。

## IIC2 整条总线不动：实机 DIAG 定位（16:00）

用户在板上观察"两条 I2C 线的 LED 都不闪"，怀疑 GPIO 没被驱动。**用 DIAG 实机取证**（COM5 直接探）：

```
>DIAG<  →  [DIAG_00_0_0_02]
             │  │ │ └─ IIC1 阵列位图 02 = 只有 0x51 ACK → 硬件 I2C 正常
             │  │ └─── 24C02 无 ACK
             │  └───── PCF 无 ACK
             └──────── OLED 未探到
```

结论：**IIC2（P5.4/P5.5）整条死**，IIC1 正常。与示例工程最初遇到的是同一类问题。

代码层两个真 bug（已修）：
1. **IIC2 用了开漏模式**。开漏的"高"完全依赖上拉，而 STC8 的内部上拉在 `P5PU`（xdata 扩展 SFR）。一旦没生效，写 1 = 悬空 → 总线永远上不去 → 整条线上三个器件全哑、看起来像"GPIO 没驱动"。改成**准双向**（`P5M1&=~0x30; P5M0&=~0x30`），与示例工程驱动 TM1637 的做法一致；`P5PU` 保留做余量。
2. **`Board_SwI2cPinsOk()` 会把总线钉死在低电平**：推挽拉低测完直接 `P5M1|=0x30; P5M0|=0x30` 切回开漏，但锁存器还停在 0，等于一直拉着 SCL/SDA 不放。修法：先把 `SW_SCL/SW_SDA` 置 1 再改模式。这个 bug 在主流程里被紧随其后的 `I2C2_Init()` 掩盖，只要在运行时再调用一次（比如诊断命令）就会永久锁死总线。

新增/变更的诊断命令：
- `DIAG` 加了第一个字段（引脚自检）：`[DIAG_<p5>_<oled>_<pcf>_<m24>_<arr>]`，`p5=0` 即 P5.4 拉不低。
- 新增 `PINS`：SCL/SDA 以 2Hz 慢闪 3 秒，纯 GPIO、不跑协议，肉眼即可判定引脚是否受控；回 `[PINS-OK]`/`[PINS-NG]`。

**还给用户的关键结论**：P5.4 出厂是 RST，STC-ISP 下载时必须勾"复位脚用作 I/O 口"（P5.4 用作 I/O），否则软件层无解。这很可能就是根因 —— 示例工程最初也是栽在这。

体积：13044 B（+104，诊断命令）。文档新增 §8「排查：IIC2 整条总线不动」。
技能 keil-c51-stc8 §6.2 补了这三条（准双向 vs 开漏 / P5.4 是 RST / 自检后先置锁存器）。

## IIC2 死总线的进一步定位：I2C_S 两张表 + P5 复位值 + 自动选组

用户回报 `[DIAG_0_00_0_0_02]`（引脚自检 0，IIC1 阵列仍有 0x51 应答），并提到"复用脚已设为 IO、示例工程里这两脚驱动 TM1637 没问题、手册里像是两个硬 IIC 通道"。

**手册核对结论（关键，之前搞混过）**：`P_SW2.I2C_S` 有**两张表**（p193 / p987）：
- 通用 STC8G（含 1K17A）：00=P1.5/P1.4，01=P2.5/P2.4，10=P7.7/P7.6，**11=P3.2/P3.3**
- **仅** 8 脚 STC8G1K08-8Pin / 08A：00=P3.2/P3.3，**01=P5.4/P5.5**，10/11 保留
所以 1K17A **没有**第二路硬 I2C，P5.4/P5.5 是纯 GPIO。示例工程那两脚能用是**因为它是 08A 的板子**。
本工程 I2C_S=3 → P3.2/P3.3 是对的（阵列 0x51 有 ACK 就是证据）。

**P5 的复位值**（p432/446）：`P5 = xx11,1111`、`P5M1 = xx11,1111`、`P5M0 = xx00,0000`
→ **P5 口复位后是高阻输入**（和 P0~P3 的准双向默认不同）。这解释了"推挽拉低也读回 1"如果模式写没生效会是什么现象。

**这版做的**：
1. `i2c_sw.c` 重写：引脚组**运行时可选**（`s_p1`），`scl_high/low`、`sda_high/low`、`sda_level()` 都按 `s_p1` 分支；`s^2` 不再依赖编译期宏。
2. `I2C2_Init()` 自动选组，规则收紧为「P5 能推挽拉低**且** 总线上有器件应答」才用 P5；否则试 P1.4/P1.5，**P1 上必须真有器件 ACK** 才切过去；都没有就回 P5 并如实上报（避免静默选错总线）。
3. `Board_SwI2cPinsOk()` 改为委托 `I2C2_PinsOk()`；`main()` 把该调用挪到 `M24_Init()` 之后（此时引脚组已定）。
4. 新增 `PINX`：`[PINX_<组>_<可驱动位图>_<P1M0>_<P1M1>_<P5M0>_<P5M1>_<P1>_<P5>_<P_SW2>]`，位图 bit0=P1.4 bit1=P1.5 bit2=P5.4 bit3=P5.5。用途是判断"模式寄存器写有没有生效"：若 P5M1 回读仍是 3F，说明写没落地。
5. 上一轮已修的 `Board_SwI2cPinsOk` 锁存器残留问题在新实现里由 `pin_cfg()` 统一保证（先置 1 再改模式）。

体积 13593 B。文档 §8 补了"两张表"澄清 + 自动兜底说明 + PINX 判读。
待用户实测 `>DIAG<` / `>PINX<` 回报，重点看 PINX 的 P5M1 回读值。

**结论：本片只解码 `I2C_S` 的最低位（P_SW2.bit4），bit5 无效；且 00→P3.2/P3.3、01→P1.5/P1.4**。与手册那两张表都不一致（手册：通用表 00→P1.5/P1.4、11→P3.2/P3.3；8 脚表 00→P3.2/P3.3、01→P5.4/P5.5）。之前一直用 3，所以硬件 I2C 一直在 P1 组，看到 0x51 其实是 24C02 —— 这解释了"8 片只认到 0x51"的怪现象。

**修复**：`CFG_I2C_S_SEL` 3 → **0**。改后 `EE_ScanMask` 才会扫到 FF（8 片）。
`ee_sa()` = 0x50 + (idx & 7)，地址映射本身没问题。

关于用户问的"P5 在原理图上存在但不可用"：`PINX` 证明 P5.4/P5.5 **写了推挽(M0=30)、锁存器写 0，读回仍是 1**（P5=30）→ 这两个脚在本片/本封装上推不动；而 IIC2 三个器件全部在 P1.4/P1.5 上应答。所以应以实测为准：IIC2=P1.4/P1.5，IIC1=P3.2/P3.3，I2C_S=0。

文档 §1 重写为实测拓扑（含 §1.1 I2C_S 实测映射表、§1.2 为什么 P5 用不了）；§8 的根因从"开漏"改正为"**引脚组选错**（器件在 P1，固件驱动 P5）"，开漏降级为次要坑。

## 初始化卡在 4%：parse_num 只收 9 位 + 阵列"假 ACK"

用户报：屏幕正常、`[DIAG_1_3C_1_1_FF]`（8 片全 ACK），但上位机初始化卡在 4%（Writing initialization info），I2C 灯不闪。

**实机复现（COM5 直连）**：
```
SET_..._1793954200_1793954200_0_...  (10 位 epoch)  -> [SET_ERR]
SET_..._17939542_17939542_0_...      (8 位)         -> [SET-OK]
GET_!  -> >INFO_CAPSA-CARD-01_00_FF_64_64_17939542_..._0_0123456789AB<
```
**根因：`parse_num` 的十进制分支写的是 `if (n >= 9) return 0`，而 epoch 是 10 位** → 第 10 位直接判错 → `SET_ERR`，固件根本走不到写 24C02（所以 I2C 灯不闪）。上位机侧表现成"卡住"（对话框停在 4%，错误行被忽略）。改为 `n >= 10`（32 位上限），编译时 C51 对 `v > 429496729UL` 报 C292，去掉该越界判断即可。

**顺带发现阵列总线是"假 ACK"**：写 16 字节到 0x50@0x0000 后读回全是 `00`；读空白区 0x01FF 也是 `00`（正常应为 `FF`）。说明 SDA 恒被读成 0 → 所有地址都会 ACK、数据全 0。即阵列位图 `FF` 不可信。原因是电气：SDA 被拉死 / 阵列板没供电（ESD 二极管钳位）/ 无上拉。
为此新增 `I2C1_BusLevels()`（关 ENI2C→GPIO 采样 P3.2/P3.3 空闲电平，bit0=SCL bit1=SDA），并加到 `DIAG` 第 6 个字段：正常必须是 `3`。

其他修复：
- `PINX` 结束时把 P1 留成高阻 → 之后 I2C2 全废。新增 `I2C2_RestorePins()` 并在 PINX 末尾调用。
- 我这边用 8 位时间戳的 SET 把卡的 meta 写成了 1970 年，用户需要重新初始化覆盖。

体积 13871 B。文档 §9 补充"位图 FF 但读回 00 = 假 ACK"的判读。

## 初始化 0/8 的真因：EE_WriteBlock 缓冲越界（16:45）

用户回报 `[DIAG_1_3C_1_1_FF_3]`（8 片全 ACK + 总线电平 3，电气已正常），但上位机初始化
结果是 **Chip health check 0/8、Array capacity 0 B / 8 KB × 0 chips**（100% 完成但全片不合格）。

**根因（确凿）**：`hardware/ee.c` 的 `EE_WriteBlock` 组装缓冲写成 `uint8_t tmp[4]`，
而一包写事务需要「2 B 片内地址 + 16 B 数据 = 18 B」→ 越界 14 字节。C51 SMALL 模式把局部
数组放 128 B 的 data 区，越界**静默**冲掉相邻的 `done` / `i` / `m`（型号指针），于是地址算错、
数据写到别的页，但 I2C 事务本身成功 → 回 `[RX-OK]`，读回全 00（连空白区也是 00 而非 FF）。
这正是上一轮"假 ACK"的后续：电气修好后仍读不回，因为缓冲越界。

修复：`static uint8_t xdata s_ew[CFG_PKT_BYTES + 2]`，并把 `chunk` 夹到 `CFG_PKT_BYTES`
（防御，正常不触发）。核对其它缓冲：`EE_ReadBlock` 的 `tmp[2]`（只放地址）安全；
`M24_Write` 的 `tmp[10]`（1 B 地址 + 8 B 页）安全；`s_pkt` 已按宏定义。

顺带确认 `INT_W`/`INT_R` 里的 `s_addr = 0` **不是 bug**：协议文档 §5.3 明确"进入读模式，指针 = 0"。

## 0/8 的第二层真因：读会话握手括号方向（17:05）

上一轮修完 `tmp[4]` 越界后，用户重跑初始化仍 0/8。实机逐步拆解（COM5）后定位到
**上下位机握手格式不一致**：

- 上位机 `CapsaProtocol.WriteAck()` 发 `[RX-OK]`（方括号）；
- 固件 `Proto_OnByte` 只认 `>` 起始、`<` 结束的帧 → 整串 `[RX-OK]` 落在帧外被丢弃；
- `Proto_Wait` 白等 `CFG_RXOK_TIMEOUT_MS`（2000 ms）超时 → 发 `[RX-ERR]` 退出读会话。

**症状特征（很好用）**：写入全部 `[RX-OK]`，读只回来**恰好一包 16 字节**，随后
`[RX-ERR]`；上位机侧表现为 `Chip health check 0/8`、`Array capacity 0 B`。
同时 `GET_!` 的 health/capacity 已被上次失败的初始化写坏成 `00` / `0`。

修复（两侧都做）：
1. 上位机 `WriteAck` 改为 `Port.Write($">{token}<")`；
2. 固件 `Proto_OnByte` 增加 `s_close`，`>` 配 `<`、`[` 配 `]`，同时处理
   "括号不配对 → 判坏帧"（避免把内容当命令执行）。老上位机也能跑通。

**实测确认**：修完后完整跑 8 片 × 2 图案（0x00/0xFF）× 256 字节，
`healthy = 8/8`，每片 `readlen=256 bad=0`。芯片测试流程本身没有问题。

顺带确认的两个"不是 bug"：
- `INT_W`/`INT_R` 里的 `s_addr = 0` 符合协议（文档写明"进入读写模式，指针 = 0"）；
- `ROUTER` 会清 `s_has_edge`，所以 `INT_W` 前必须先 `ADDR`（上位机 `WriteMemory`
  确实先发 `SelectChip` + `SetEndAddress`，顺序正确）。

## 格式化复用写入流程 + 掉线心跳 + Stop 按钮（11-07 13:00）

用户三点：① 格式化应复用普通写入（数据全填 0x00）以获得一样的进度/直观性；② 检测串口掉线并让界面回到未连接；③ 写入/读取缺中断按钮。

1. **格式化复用写入**：WritePanelViewModel 提取 `RunWriteSessionAsync(byte[] payload, bool formatMode)`（原 WriteVerifyAsync 主体）。FormatAsync = `new byte[_device.ArrayEffectiveBytes]` → RunWriteSessionAsync(zeros, formatMode:true)。走完整 WriteAsync + VerifyAsync（进度/卡片/速率/Stop 全一致），收尾 formatMode 分支：UG_0 + DI(全0, 原次数)。
2. **掉线检测**：CapsaProtocol.WriteFrame 记录 `LastActivityMs`；CapsaSerialPortService 加 3s Timer 心跳 —— 端口不在 GetPortNames 立即断；最近 1.5s 有活动则跳过（让路给读写会话）；否则 Ping(500)，连续 2 次失败 → DropConnection → ConnectionChanged(false, reason)。`SerialConnectionChangedEventArgs` 加 `Reason`。**TopBarViewModel 原先没订阅 ConnectionChanged**（只有它自己发 ConnectedChanged），补订阅：掉线→IsConnected=false + StatusText "Device lost (reason)" + ConnectedChanged(false)，主界面 OnConnectionChanged 复位 DeviceInfo/Board。
3. **Stop 按钮**：ITransferService 加 `RequestAbort()`（发 protocol.Abort(400)）+ Mock 空实现。WritePanelViewModel/ReadPanelViewModel 加 `_cts` + `[ObservableProperty] IsCancelable`，token 传给 WriteAsync/VerifyAsync/ReadAsync/SetUsedSpace/SetDataInfo；CancelWrite/CancelRead = RequestAbort + Cancel（先 ABORT 再取消，否则固件白等 2s RX-OK）。XAML 两个面板按钮区改 StackPanel 横向 + `Classes="danger"` 的 Stop（IsVisible=IsCancelable）；Controls.axaml 新增 danger 样式（Warn 色描边）。
   踩坑：替换 FormatAsync 时 old 字符串漏掉了方法末尾的 `}`，导致多一个 `}`（CS1022）—— 已删。DeviceInfoViewModel 需补 `ArrayEffectiveBytes`/`ProtectedChips` 转发属性给 VM 用。
4. 验证：mock 截图（shot16/w0-writing-early）显示 Stop 橙色按钮在写入中可见、Card capacity 192 KB (6/8 chips)、黄段、卡片黄；0 Error 0 Warning。

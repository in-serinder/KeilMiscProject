## 固件：未初始化卡在 OLED 上显示存储卡属性（已修）

**根因**：`App_Tick()` 的每秒周期探测用 `M24_Read(0x00,&flag,1) && (flag & 0x01)` 判定就绪，
而 main / `UI_Boot` 用检测区（0xF6~0xFF 非全 0xFF）判定。空白 24C02 读回 `0xFF`，
`0xFF & 0x01 == 1` → 未初始化卡被误判 READY，约 1 s 后屏幕自动画出容量/型号，
把 `UI_Boot` 画的"未初始化"画面覆盖掉。存在**三套不一致判据**是问题反复出现的根源。

**修复（三层）**：
1. `user/meta.c/.h` 新增 `Meta_InfoValid()`：唯一"可展示属性"判据 =
   检测区非全 0xFF && `init_flag == 0x01` && `medium <= 3` &&
   `model_kbit` 属于已知型号表 && `cap_kb` ∈ 1..4096。
   `main`（元数据加载）、`UI_Boot`、`App_Tick` 全部改用它。
2. `user/ui.c` 新增总闸 `s_card_ok` + `UI_SetCardReady(bit)`：
   `line_model()` / `UI_Capacity()` / `UI_Progress()` / `UI_Idle()` /
   `UI_RefreshMeta()` 开头全部检查，未就绪时任何路径（UG / ABORT / TX-OVER）都画不上属性。
3. `hardware/ssd13xx.c` 新增 `OLED_Clear()`：四页全灭 + 差分缓存标脏（填 `0x01`）
   + `s_bar_pct = 0xFF`，保证切换画面时上一张卡的容量/型号/进度条被彻底抹掉。
   `UI_Uninit()` / `UI_CardState(0)` 改为 Clear + 四行纯提示（含 `Capacity unknown`）。

**附带**：
- `s_card_state` 初值改 `0xFF`（未知），修复"首帧状态与初值相同 → 早退不刷新"。
- `handle_int_w()` 加 `Meta_InfoValid()` 前置检查（`SET_ERR`），未初始化卡不许开写入会话。
- `App_Tick` 在在线但 `!g_meta.init_flag` 时补一次 `Meta_Load()` + `EE_SetModel` + `PCF_SetMask`
  （卡是后来才插上的场景，否则屏上显示的是 main 的默认值）。
- README 第 172~215 行三态表与判据说明同步重写。

**构建**：`"/d/Keil_v5/UV4/UV4.exe" -b capsa.uvproj -j0 -o build_check.log`
→ 0 Error / 0 Warning，data=74.3 xdata=765 code=15243（Keil 装在 D:\Keil_v5）。

**教训**：同一语义（"卡初始化了吗"）在固件里只允许有一处实现。多点判定必然漂移，
而漂移的表现是"改了没效果"——上一轮改 `UI_Uninit` 无效正是因为它被另一处判定覆盖。

## 上位机：格式化重做（进度条 + 容量清零 + SET 9 字段）

**现象**：点 `Format card` 没进度条、格式化后容量还在。**根因**：Format 按钮
`IsEnabled="{Binding IsReady}"`，而 `IsReady = _device.IsInitialized` —— 卡未初始化时
按钮是灰的，点了什么都不发生（上一轮正在处理未初始化卡，正好踩中）。

**实现**（`WritePanelViewModel.FormatAsync` 重写）：
1. **不再要求卡已初始化**：按钮改绑 `IsNotBusy`；未初始化时先发 `SET_`（9 字段）
   把属性建起来（固件 `INT_W` 前校验 `Meta_InfoValid()`，没属性开不了会话），
   然后再取几何。**顺序必须是 SET → 取几何**，反过来会永远卡在 "geometry unknown"。
2. **范围 = 每片完整地址空间**：`payload = writable × CapacityBytes`，按
   `0x0000..chipBytes-1` 逐片写 0x00（不再用 `ArrayEffectiveBytes` 这种二义口径）。
   状态栏显示 `6 writable chip(s) × 32.0 KB = 192.0 KB · 0x0000–0x7FFF per chip`。
3. **收尾三步全部检查返回值**：`SET`（时间戳/属性）→ `UG_0`（容量归零）→
   `DI_<16 个 0>_<原次数>`（哈希失效、次数保留）。任一步失败写进状态栏
   `Formatted with warnings · … UG 0 rejected`（以前是静默的）。
4. 收尾后本地 `BeginWrite()` + `SetLiveUsedBytes(0)` 再 refresh，卡片与左侧占用当场清零。

**新增**：`IDeviceService.ConfigureCardAsync(CapsaInfo)` —— 读-改-写，
健康掩码与 WP 掩码以卡上现有值为准（格式化不是健康检查，不能顺手"修复"芯片）。
`MockDeviceService` / `MockTransferService` 同步：mock 传输现在按 8 片给出
`ChipAddress`，卡片进度条在无硬件时也能逐片走动。

**坑**：`ParseModelKbit("24C64")` 不能直接抽数字（会得到 2464），必须先切掉 `24C`
前缀；UID 必须清洗成 12 位 hex（mock 的 `3F9C-E1D4-…` 带连字符，固件 parse_uid 会拒）。

**构建**：`dotnet build Capsa/Capsa.csproj --no-restore` → 0 Error / 0 Warning。
注意 `Capsa.exe` 运行中会锁 bin，构建前必须先关进程；`-t:Compile` 可在不关进程时验语法。

  `Meta_RecalcCapacity()` 重算 `g_meta.cap_kb` 并随 SaveInfo/FirstSet 落盘。

  WP 点击的 SET 没有容量字段，重算是唯一入口。

  `line_model()` 的 `x8` 改为可写片数（`24C64x6`）。
- `main` 默认 cap_kb 也走 `Meta_RecalcCapacity()`（wp=0 → 8 片，口径单点出口）。
- 固件 0E/0W，code=15321。

**不再用 24C02 的 cap_kb** —— 固件 cap_kb 现在是有效容量，若还塞进
`ArrayTotalBytes`（百分比/进度条基准）会与 `ArrayEffectiveBytes` 双重扣除。
两口径分工：`ArrayTotalBytes` 恒 8 片（基准），`ArrayEffectiveBytes` 自己扣 WP。

## 读会话被心跳打断（第五轮，协议追踪定位）

**用户贴回错误详情日志**：`INT_R -> [RX-OK]` 后 2 秒出现 `TYPE-CAPASA -> <no reply / timeout>`。
**根因**：心跳判忙只看 `LastActivityMs`（最后一次**写**命令），读会话中上位机十几秒
只收不发 → 1.5s 后误判空闲 → 心跳线程发 probe，与传输线程**并发抢同一串口**，
[YES] 与 R_ 数据帧互相污染 → ReadFrame 2s 超时 → ReadMemory 返回 null。
（ReadMemory 对非 R_/TX-OVER 帧直接 return null，[YES] 一到就完。）

**修复**：
1. `CapsaProtocol` 加 `_sessionDepth` + `IsSessionBusy`；`WriteMemory`/`ReadMemory`
   （后者拆出 ReadMemoryCore）try/finally 进出会话。
2. 心跳 `HeartbeatTick`：`protocol.IsSessionBusy` 时强制 return（与 BusyWindowMs 并列）。
3. `ReadFrame` 每收到一个字节就刷新 `LastActivityMs` —— 读也是总线活动（双保险）。

**方法论（值得沉淀）**：协议追踪把"猜"变成"看"——2 秒间隔的那条 TYPE-CAPASA
一眼锁定心跳；没有追踪时这类偶发超时基本无法定位。

## 空闲时检测端口消失/被占用（第六轮，用户提议）

**用户提议**：无任务空闲时检测串口是否还存在/被占用，否则界面转断开。
**现状盘点**：端口消失检测（GetPortNames）已有；会话抑制已有（IsSessionBusy）；
缺的是**"被占用/被移除"的确定性故障立即断开**——之前 probe 抛的
UnauthorizedAccessException/IOException 被吞，走"连续 2 次无响应"路径且原因只显示 no response。

**实现**：
1. `CapsaProtocol.LastPortError`：ReadFrame 的 catch 分流——
   UnauthorizedAccessException/IOException 记入 LastPortError（读阶段异常冒不出协议层），
   其余照旧吞掉返回 null；`ClearPortError()` 供心跳每轮清零。
2. 心跳：Write 抛的两类异常直接分类；Ping 返回 false 再查 LastPortError；
   命中即 `DropConnection(portName, "port taken or removed · <原因>")`（不给 2 次机会），
   顶栏 `Device lost (port taken or removed · 拒绝访问端口 COMx)`。

**注意**：Windows 串口独占——我们已连接时别的程序一般打不开口；
真实场景是 USB 热插拔导致句柄失效（IOException）和权限类异常。
"我们未连接、别的程序占用"在 Connect/Probe 阶段已被 LastProbeError 覆盖。

**用户实测**：拔掉 COM8（设备管理器已消失），界面仍 Connected —— 心跳没起作用。
代码走查未能定位心跳失效的确切原因（GetPortNames 路径与 Ping 异常路径理论上都会触发
DropConnection；嫌疑最大的是心跳线程卡死 / Timer 失效，但无法从用户侧取证）。

**修复策略：不再依赖单一心跳，加 UI 线程看门狗**：
- `ISerialPortService` 新增 `LastHeartbeatTickMs` / `IsPortPresent()` / `DropNow(reason)`，
  Mock 同步实现（Mock 永远 alive/端口在）。
- `MainWindowViewModel` 起 UI DispatcherTimer（4s）：
  1. 已连接端口不在 GetPortNames → `DropNow("port disappeared")`；
  2. 心跳 12s 没跳动（正常 3s）→ `DropNow("watchdog · heartbeat stalled")`。
  看门狗跑在 UI Dispatcher 上，与心跳（ThreadPool Timer）完全独立 ——
  "兜底必须不与被兜底者共享生命周期"。

**方法论**：任何"后台线程负责报告故障"的设计，都需要一个不共享其生命周期的
UI 侧看门狗；心跳死了没人管心跳，是最典型的单点失效。

## 第二次拔线不再断开（第八轮，取证加固）

**用户实测**：第一次拔线能自动断开（watchdog 生效），重连后第二次拔线就不断了。
纯走查无法定位（各路径理论上都会断），转为**取证加固**：

1. **心跳 tick 间隔自监控**：gap > 9s（3 倍周期）→ ErrorLog.Add
   "heartbeat thread was stalled" —— 心跳半死不活（驱动挂死/ThreadPool 饥饿）会留证据。
2. **掉线历史进 ErrorLog**：DropConnection → "Heartbeat · connection dropped · <reason>"，
   DropNow → "Watchdog · ..." —— 每次断开的原因永久可查（Logs 按钮）。
3. WatchdogTick 由 async 改同步（无 await，消除 CS1998 与未观察异常）。

**用户上一轮测的是第六轮版本**（只有 LastPortError，无 watchdog、无停摆检测）；
第七轮的 watchdog（4s 端口消失 + 12s 停摆接管）是本轮对话刚构建的，用户尚未测过。

**教训**：修"偶发不掉线"这类问题时，第一轮就该把诊断埋进去，而不是先修再等复现。

## 占用记录先清原则（第九轮，用户设计决策）

**用户核心观点**：任何破坏完整性的操作（写入中断/失败、格式化、健康检查）本质上
都是对存储清 0 —— UG 清占用应该**先行**，而不是失败后补偿。补偿依赖上位机活着，
崩溃/断线/断电时没机会跑，卡上就残留"还有完整数据"的假象。

**实现（"先清 + 兜底"双层）**：
- 完整格式化：`RunWriteSessionAsync` 开头立即 UG_0（CancellationToken.None），
  `_usedClearedDuringWrite = true`。
- 普通写入：`FlushProgress` 里首包确认（percent > 0 且未清过）→ fire-and-forget
  `ClearUsedAfterFirstPacketAsync()`（只 UG_0 不动哈希）；**成功上报 UG_n 前必须
  await `_usedClearTask`**，否则 UG_0 晚到把正确记录覆盖回 0（关键防乱序）。
- 失败/校验失败/取消：条件改为 `_wroteAnyBytes && !_usedClearedDuringWrite`
  （原来 `formatMode && _wroteAnyBytes` 漏了普通写入）→ `EnsureUsedClearedAsync`
  （原 ResetUsedAfterInterruptedFormatAsync 泛化：UG_0 + DI 清哈希 + 本地归零）。
- 芯片健康检查：`ChipHealthViewModel.StartTestAsync` **测试开始时** UG_0
  （整片覆写图案 = 破坏性同格式化），原"成功后清"保留为双保险。

**设计教训**：破坏性操作的元数据清理必须与破坏同起点，"事后补偿"只配当兜底。

## 写会话中插 UG_0 = 协议灾难（第十轮，协议追踪定案）

**用户贴追踪**：payload 98 B 写 0x50，首包后的后台 UG_0（上一轮"先清"实现）插进
W_ 流：应答撕裂 `[RX-OK\r\nUU-OK]`、下一个 W_ 包 2s 超时、写入失败；
第二次尝试 UG_0 timeout 1594ms 后 W_ 也超时。

**根因**：这套协议是**半双工主从式**——写会话中固件流式处理 W_ 包，
UG_0 的处理还要写 24C02（EE 写 + ACK polling），阻塞主循环 → 应答延迟/丢失；
且上位机两个线程并发写同一串口 → 字节流交叉、帧撕裂。

**修正（回归"会话开始清"）**：
- 普通写入与格式化统一：**RunWriteSessionAsync 开头（固件空闲态）UG_0**，
  `_usedClearedDuringWrite = true`。
- **删除**首包后后台清（ClearUsedAfterFirstPacketAsync / _usedClearTask / 成功路径 await）。
- 失败兜底条件不变（`_wroteAnyBytes && !_usedClearedDuringWrite` → EnsureUsedClearedAsync）。

**铁律（已写进 README 与代码注释）**：半双工主从协议中，任何命令只能在自己会话
之外发；会话中插命令 = 撕裂应答 + 超时。"先清"原则的"先"= 会话开始，不是首包后。

## 文本编辑器行号栏（第十二轮）

**用户需求**：主页文本编辑器（Plain text / Dual view 右侧）左侧加行号，类似代码编辑器。

**实现**（TextEditorView）：
- 布局改 `ColumnDefinitions="Auto,*"`：左 gutter（SurfaceAlt 底 + 右分隔线）+ 右 TextBox。
- gutter = 单个 TextBlock，内容 "1\n2\n…\nN"（每行一个行号），字体/字号与 TextBox.code
  完全一致（Cascadia Mono 12px），**不设 LineHeight**（用字体默认度量，与 TextBox
  内部 TextPresenter 天然一致，避免长文档滚动累积错位）。
- 滚动同步：AttachedToVisualTree 后从 TextBox 视觉树找 ScrollViewer（GetVisualDescendants，
  需 using Avalonia.VisualTree），订阅 ScrollChanged → GutterText.RenderTransform
  (TranslateTransform).Y = -Offset.Y（注意 Avalonia 11 的 ScrollChangedEventArgs
  没有 Offset 属性，要从 sender 取 Offset）。
- 性能：每次文本变化只做 O(n) 换行计数，**行数不变不重建字符串**；VM 加载内容
  （导入/读取）也经 GetObservable(TextBox.TextProperty) 刷新（Subscribe 需传
  AnonymousObserver——Avalonia 11 无 Action 重载）。
- HEX 模式不加（HexView 控件自带地址列）。

## 行号栏不滚动修复（第十三轮）

**用户实测**：行号永远停在 1-18，编辑器滚动时行号不动。

**两个原因**：
1. **GutterText 被拉伸**：TextBlock 默认 VerticalAlignment=Stretch，被 arrange 成
   可视区高度（18 行），只渲染 18 行 —— 平移也只是在 18 行内挪。修复：
   `VerticalAlignment="Top"`（arrange 高度 = 内容全高，渲染全部行）。
2. **滚动事件挂接不可靠**：AttachedToVisualTree 时 TextBox 模板可能还没应用，
   GetVisualDescendants 找 ScrollViewer 返回 null。修复：改用路由事件
   `TextHost.AddHandler(ScrollViewer.ScrollChangedEvent, ...)`（内部 ScrollViewer
   的 ScrollChanged 冒泡上来），e.Source as ScrollViewer 取 Offset
   （ScrollChangedEventArgs 没有 Offset 属性）。

**Avalonia 教训**：TextBlock 默认 Stretch 会被压成容器高度（长内容只渲染可视部分）；
要平移显示全部内容必须 Top 对齐。模板内部控件的模板应用时机不可靠，
路由事件 AddHandler 比视觉树查找稳。

## 行号超 18 行消失修复 + 快速健康检查（第十四轮）

**行号 18 行后空白（根因确认）**：没有滚动容器时，TextBlock 的 measure 高度被限制为
可视区 → **长内容只布局/渲染前十几行**（VerticalAlignment=Top 治标不治本，measure
约束才是源头）。修复：gutter 包一层 `ScrollViewer`（VerticalScrollBarVisibility=Hidden，
ScrollViewer 给 child 的 measure 高度是无限），编辑器滚动时直接
`GutterScroll.Offset = new Vector(0, editorScroll.Offset.Y)`；ScrollChanged 里用
`e.Source` 排除自身（设置 GutterScroll.Offset 会再触发事件，防无限循环）。
TranslateTransform 方案整体弃用。

**健康检查窗口加 Quick check 按钮**：`ChipTestOptions.TestLengthBytes = 256`
（只测每片前 256 字节，秒级；整片= 0 仍是 "Start test"）。
`StartTestAsync` 泛化为 `RunTestAsync(fullChip)`；PrepareSpeedometer/SampleSpeed
按 tested = min(256, capacity) 折算速率与进度；清 0 逻辑（UG_0 先行）两种模式共用。

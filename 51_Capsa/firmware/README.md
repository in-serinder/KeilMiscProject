#firmware — Capsa 存储卡下位机固件

STC8G1K17A（17 KB Flash / 256 B idata / 1 KB xdata，22.1184 MHz，115200 8N1）
直接对接 `Capsa` 上位机，协议见 `../CapsaSim/docs/COMMAND_REFERENCE.md`。

## 1. 硬件拓扑

> 下表是**实测确认**的结果（`>SCAN<` + `>PINX<` + `>DIAG<` 上板验证），
> 与最初按手册推断的接线不同：本板的 IIC2 实际在 **P1.4/P1.5**，
> 而 P5.4/P5.5 在这颗片子上**不可驱动**（见下方说明）。

| 总线 | 引脚 | 驱动方式 | 挂载设备 |
| --- | --- | --- | --- |
| IIC1 | **P3.2=SCL / P3.3=SDA** | **硬件 I2C**（`P_SW2.I2C_S=0`，251 kHz） | **仅** 8 × 24Cxx（0x50~0x57）—— 纯存储器总线 |
| IIC2 | **P1.4=SCL / P1.5=SDA** | **软件 I2C**（准双向位操作，~200 kHz） | 24C02（**0x51**，属性存储）、PCF8574T（**0x20**，8 路写保护）、SSD1315（**0x3C**，128×32 OLED） |
| UART1 | P3.0=RXD / P3.1=TXD | 定时器 1（12T，reload 0xFFFC） | 上位机 |

> **IIC1 / IIC2 分工**：IIC1 只做存储器阵列的数据通路，上面不挂任何控制或
> 显示器件；显示、写保护控制和属性存储三种功能全部集中在 IIC2。三条地址
> （0x51 / 0x20 / 0x3C）互不冲突，单主顺序访问，无需分时切换。

### 1.1 `I2C_S` 实测映射（与手册不一致，以实测为准）

`>SCAN<` 把 `P_SW2.I2C_S` 的四种取值各扫一遍，本板结果：

| `I2C_S` | 实际引脚 | 扫描结果 |
| --- | --- | --- |
| 0 或 2 | **P3.2 / P3.3** | 位图 **FF**（8 片阵列全部应答）、无 OLED |
| 1 或 3 | **P1.5 / P1.4** | 位图 02（只有 0x51 = 24C02）、能看到 OLED |

结论：**本片只解码 `I2C_S` 的最低位（`P_SW2.bit4`），bit5 无效**，而且
`00` 指向 P3.2/P3.3 —— 与手册"通用 STC8G：00→P1.5/P1.4、11→P3.2/P3.3"
那张表**不一致**（手册里列出的 P2/P7 分组在本封装上也不存在）。
所以 `CFG_I2C_S_SEL` 取 **0**，阵列才在 P3.2/P3.3 上。

> 换片子/换板时先跑 `>SCAN<`，别照抄手册表。

### 1.2 为什么 P5.4/P5.5 用不了

`>PINX<` 报告：`P1.4/P1.5` 推挽拉低能读回 0，而 **`P5.4/P5.5` 写了推挽、
锁存器写 0，读回仍是 1**（`P5M0=30 / P5=30`）。这说明这两个脚在本片/本封装上
没有真正引出到可驱动的 IO 焊盘（不是"模式没配对"）。因此：

* 固件不再假设 IIC2 一定在 P5，而是**上电自动选组**：先用 P5，若拉不低或
  总线上没有器件应答，就切到 P1.4/P1.5（`I2C2_PinPair()` 可查询当前用哪组）。
* 本板实测落在 **P1 组**，OLED / PCF8574 / 24C02 全部在这条线上应答。

### 3.1 体积预算（想再砍时按这张表下手）

| 项目 | 大小 | 说明 |
| --- | --- | --- |
| `?C?LIB_CODE` | 779 B | C51 运行库：16/32 位乘除、移位。用 32 位运算就会带进来 |
| 8×8 字库 | 760 B | 95 字符 × 8 B，唯一字库；砍到 64 字符可再省 248 B |
| `handle_set` | 659 B | 9 字段切分 + 逐字段解析（协议最复杂的一段） |
| `app_handle` + `?PR?APP` | ~900 B | 命令分发 + 各 handle 函数 |
| meta 读 / 写 / 首建 | ~950 B | 9 字段与 44 字节 EEPROM 布局互转 |
| I2C / EE / OLED | ~1.6 KB | 硬件 I2C、软 I2C、页写、OLED 初始化 |

演进：初版 16 959 B → 去掉 8×16 字库与通用像素绘图 14 028 B → 优化等级 8→9 后 12 909 B。
**不要为省 Flash 去动 32 位运算**：EE 地址、UG 计数、ADDR 边界都依赖它，
`?C?LIB_CODE` 省不掉，硬拆只会让代码更长。

### 4.1 `DIAG` / `PINS`：分线"屏黑 / 属性读不到 / 总线不动"

屏全黑、`GET_!` 回 `[SET_ERR]`、或两根 I2C 线上一点电平变化都看不到时，
先用串口助手发 `>DIAG<`，五个字段：

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| P5 引脚 | `1` / `0` | `1` = P5.4/P5.5 能推挽拉低并读回（真在 CPU 手上）<br>`0` = **拉不低** → P5.4 还是复位脚 |
| OLED 地址 | `3C` / `3D` / `00` | `00` = 没探到（未接 / 地址不符 / 总线不通） |
| PCF | `1` / `0` | 0x20 是否有 ACK（写保护控制器） |
| 24C02 | `1` / `0` | 0x51 是否有 ACK（属性存储器） |
| 阵列位图 | `FF` / `01` … | IIC1 上 8 片 24Cxx 的应答位图（bit0=0x50） |
| 总线电平 | `3` / `2` / `1` / `0` | IIC1 空闲电平：bit0=SCL(P3.2) bit1=SDA(P3.3)，**正常必须是 3** |

判读：

* **P5 引脚 = `0`** → 这是最常见的死因：STC-ISP 下载时"复位脚用作 I/O 口"
  （P5.4/RST 选项）没勾，P5.4 永远是复位脚，IIC2 的 SCL 出不来，整条总线死掉。
  **重新下载并勾选该选项即可**，软件层面无解。
* P5 = `1` 但三项器件全 `0` → 总线电平不对：查 P5.4/P5.5 到器件的连线、模块上的
  4.7K 上拉、以及器件供电。
* 只有 OLED 是 `00` → 屏地址不是 0x3C/0x3D，或屏没插好（PCF/24C02 有 ACK 说明总线通）。
* 阵列位图是 `00` → IIC1 上没有任何片子应答（P3.2/P3.3 接线或供电）。
* **阵列位图是 `FF` 但读回全是 `00`（空白区本该是 `FF`）** → 这是"假 ACK"：
  总线电平字段一定 `≠ 3`。SDA 被拉死（短路 / 器件的 ESD 二极管在没供电时
  把线钳在 0）时，主机每采样一次都读到 0，于是所有地址都"ACK"、读出的数据
  全是 0x00。先量电气，别怀疑协议。

`>PINS<` 是纯 GPIO 测试，不涉及 I2C 协议：两条线会以 2 Hz 慢闪 3 秒。
看到闪烁 = 引脚受控，问题在器件侧；完全不闪 = 引脚没受控（同上，查 ISP 选项）。


**与文档的差异（以实际硬件为准）**：PCF8574T 接在 **IIC2、地址 0x20**，
文档里模拟器用的是 `0x58 / I2C2` —— 总线一致、地址不同。上位机从不直接
寻址 PCF8574（只通过 `SET` 的 WP 字段间接控制），所以这种差异对协议无影响。

## 5. OLED 显示（128×32，四行 8×8）

```
页 0  Write 0x53  68%     ← 任务状态 + 芯片地址 + 任务百分比
页 1  ████░░░░░░░░  30%   ← 进度条(96px) = 容量占用 + ★行末占用百分比
页 2  19.5/64.0KB        ← 已用/总容量（1 位小数）
页 3  24C128x8 EEPROM    ← 型号 × 片数 + 存储介质（跟随 24C02 元数据）
```

**语义约定**：

* **进度条 = 容量占用，不是任务进度**。任务进度只体现在页 0 的百分比；
  写入完成后上位机经 `UG` 上报新占用，页 1 / 页 2 才一起增长。
* 型号行、容量行的数据源都是 24C02 元数据；`SET` 成功后固件立即重绘这两行
  （`UI_RefreshMeta`），上位机把卡改成 24C128 时屏上当场更新，不用重启。
* **进度条行末的占用百分比**与进度条在同一页（条区 0..95、文字区 96..127
  一次事务发出）；页 2 只放容量数字，不重复百分比。
* **存储介质显示**：页 3 末尾跟 `EEPROM / FRAM / EERAM / SRAM`（与上位机
  `StorageMediumCatalog` 的显示名一致，数据来自 24C02 的 medium 字段）。
* **★ 容量与片数都是"可写片"口径**：点 WP 后（`SET_!_<mask>_!…_!`，其余字段占位），
  固件在 `handle_set` 末尾调 `Meta_RecalcCapacity()` 把 `cap_kb` 重算为
  **可写片数 × 单片容量** 并落盘；`UG` 的上限、屏上容量行（`Meta_ArrayBytes()`）、
  型号行的片数（`24C64x6` 这种）全部随之变化 —— WP 掉的片不算容量。
  以前型号行固定 `x8`、容量行固定 8 片口径，写保护后显示的是虚容量。
* **存储卡三态显示**（主循环空闲时每约 1 s 探测一次 24C02，连续 3 次失败
  才判离线防抖；探测只在空闲态进行，读写会话中不碰总线）：

  | 状态 | 判定 | 显示（四行全文，不含任何容量/型号） |
  | --- | --- | --- |
  | 未插卡 | 24C02 / PCF8574 无应答 | `No card` / `Insert card` / `Capacity unknown` / `CARD OFFLINE` |
  | 未初始化 | 24C02 可通讯但 `Meta_InfoValid() = 0` | `Not initialized` / `Init in Capsa` / `Capacity unknown` / `UNINITIALIZED` |
  | 就绪 | 可通讯且属性自洽 | 正常空闲显示（容量 / 型号）|

  **`Meta_InfoValid()` 是"能不能展示属性"的唯一判据**，必须同时满足：
  检测区（0xF6~0xFF）非全 `0xFF`、`init_flag == 0x01`、`medium <= 3`、
  `model_kbit` 属于已知型号、`cap_kb` 在 1..4096 之间。

  三个调用点（`main` 的元数据加载、`UI_Boot` 上电判定、`App_Tick` 周期探测）
  必须用同一个函数。**不能用"读 0x00 看 bit0"来判定**：空白 24C02 读回来是
  `0xFF`，`0xFF & 0x01 == 1`，未初始化的卡会被误判成就绪 —— 屏上一秒后就会
  冒出 `64.0KB` / `24C64x8` 这些并不属于这张卡的数据。

  另外 UI 层有一道总闸 `s_card_ok`：`UI_Uninit()` / `UI_CardState(0)` 关门，
  `UI_CardState(1)` / `UI_SetCardReady(1)` 开闸。`line_model()`、`UI_Capacity()`、
  `UI_Progress()`、`UI_Idle()` 开头都检查它 —— 任何路径（`UG`、`ABORT`、
  `TX-OVER`、`UI_RefreshMeta`）都不可能把属性画到未就绪的屏上。

  切到未插卡/未初始化画面时先调用 `OLED_Clear()`：四页全灭，并把差分缓存
  标脏（内容填 `0x01`）、`s_bar_pct` 复位 `0xFF`，保证上一张卡的容量、
  型号、进度条被彻底抹掉，后续重绘也不会被"内容没变"吃掉。

  上位机完成初始化（`SET` 成功）后固件立即切回正常显示，无需拔插或重启。

* **刻意只用 8×8 点阵**：四页正好四行，不再保留 8×16 字库（那一份就占 1.5 KB Flash）。
  屏只有 128×32，8×16 的两行大字在 1.5 米外并没有明显收益，却要吃掉近 10% 的程序空间。
* 驱动只提供 `OLED_Text()` / `OLED_Bar()` / `OLED_Clear()` 三个入口，没有通用像素绘图；
  进度条直接按整行字节拼（空心列 `0x81`，实心列 `0xFF`），一次 I2C 事务刷一页。
* **按页差分刷新**：驱动为四页各缓存 16 个字符的期望内容（另加一个"当前进度条
  百分比"），每次重绘先比较——
  * 内容没变 → 直接返回，**一个字节都不发**；
  * 变了 → 只重建并刷这一页，其余三页完全不动。

  所以"Read 0x50 45%"只改状态行时只发页 0，"进度条推进"只发页 1，容量行
  和型号行在读写过程中保持不变就不发。视觉上不会有整屏闪动，也不会因为刷
  一页而顺带重发另外三页（每页 130 字节 ≈ 6 ms）。
* 状态行按 **2% 步进**节流；配合按页差分，单步只发状态行那一页（约 6 ms），
  进度条 / 容量行在任务进行中保持不动。
* 上电自检：`I2C2 PIN ERR`（P5.4 被配成复位脚）/ `Capsa ready` / `Not initialized` / `No card`。
* 驱动入口：`OLED_Text()` / `OLED_Bar()` / `OLED_Clear()`（整屏清空 + 缓存标脏）。
* 写保护命中时状态行显示 `Write Protected`。
* 屏地址上电自动探测 **0x3C / 0x3D**；都没有则置 `OLED_Found = 0`，UI 层直接跳过绘制。

## 5A. 总线速度与写等待（可调宏，均在 `system/board.h`）

| 宏 | 默认 | 含义 |
| --- | --- | --- |
| `CFG_I2C_SPEED_KHZ` | **400** | 阵列总线目标时钟：`250` / `400` / `1000` 三档，自动换算 MSSPEED |
| `CFG_EE_ACK_POLL` | **1** | 写周期等待策略：1 = ACK polling（推荐），0 = 固定延时 |
| `CFG_EE_WR_WAIT_MS` | 5 | 固定延时模式的等待时间，也是 polling 的超时兜底 |
| `CFG_EE_ACK_POLL_TMO_MS` | 10 | ACK polling 的保底超时 |

实测频率：250 → 251.3 kHz；400 → 395.4 kHz；1000 → 921.6 kHz
（公式 `f = FOSC/2/(MSSPEED×2+4)`，FOSC = 22.1184 MHz）。

**5V 供电的 24Cxx 可以开 `CFG_I2C_SPEED_KHZ = 1000`**（5V 版才有 1 MHz 规格，
1.8V/2.5V 版只到 400 kHz）。开 1 MHz 的前提：走线短、上拉强（1~2.2 kΩ）。
开启步骤：改宏 → 烧录 → 跑一次**初始化**（芯片测试会整片写读校验，
8/8 通过即稳定；出现 `Chip health check < 8` 就退回 400）。

**ACK polling** 取代固定 5 ms 干等：写事务结束后轮询器件 ACK（tWR 期间芯片
不应答，写完立即应答），典型 1~2 ms 返回，整卡写入时间约省一半。超时 10 ms
后自动退回固定延时，防廉价芯片误 ACK。怀疑芯片兼容性（写后读回数据不对）时
把 `CFG_EE_ACK_POLL` 改 0 排除。

| 软件 I2C 速率 | `CFG_SW_I2C_DELAY = 6`（约 200 kHz）。线长/上拉弱时调大到 10~12 |
| 24C02 写周期 | 统一按 5 ms；若个别片子写失败，把 `M24_Write` 里延时改 10 ms |
| 阵列型号 | 默认 24C64；插 24C128/256/512/1024 时由上位机 SET 型号字段切换 |

## 7. 排查：发命令完全没反应

按顺序查，绝大多数"发 `>TYPE-CAPASA<` 没有任何返回"都卡在前三项：

1. **总中断 `EA` 必须为 1**（本版已修）。串口接收走中断：`Uart1_Isr` →
   `Proto_OnByte`。`EA=0` 时 RI 置位后没人取走，下一字节直接覆盖 SBUF，
   帧永远组不起来 —— 表现就是"所有命令都没反应"，但 OLED 显示正常
   （显示不依赖中断，这是最容易误判的地方）。
2. **STC-ISP 里的 IRC 必须是 22.1184 MHz**。波特率按 12T 定时器 + 重装值
   0xFFFC 算出 115200（误差 0%）；IRC 若选成 11.0592 / 24 MHz，收到的全是
   乱码，看起来也像"没反应"。
3. **USB-TTL 的 TX/RX 与板子交叉接**，GND 必须共地；串口助手 115200 8N1，
   不要开流控。
4. 串口助手若自动追加 `\r\n`，`<` 之后的部分在帧外，会被当噪声丢弃，不影响解析。
5. 帧必须以 `>` 开头、`<` 结尾：`>TYPE-CAPASA<` → 应回 `[YES]`。
   只回 `[RX-ERR]` 说明帧收到了但命令名不匹配（多余空格最常见）。
6. OLED 首行显示 `I2C2 PIN ERR` = ISP 把 P5.4 当成了复位脚
   （下载选项里"复位脚用作 I/O"要选为 I/O）。


## 8. 排查：IIC2 整条总线不动

现象：OLED 全黑、`GET_!` 回 `[SET_ERR]`、PCF 与 24C02 都不应答，P5.4/P5.5
一点电平变化都没有；而 IIC1（P3.2/P3.3）正常。

> **先澄清手册里最容易看错的一处**：`P_SW2.I2C_S` 有**两张表**。
> 第二张（`01 → P5.4/P5.5`）只适用于 **8 脚 STC8G1K08-8Pin / 08A**；
> 1K17A 用第一张，`P5.4/P5.5` **没有任何 I2C 复用功能**，就是普通 GPIO。
> 1K17A 的 I2C 引脚组只有 `00=P1.5/P1.4`、`01=P2.5/P2.4`、`10=P7.7/P7.6`、
> `11=P3.2/P3.3` 四组，且**只有一个 I2C 外设**（不是两路独立通道）。

**本版的自动兜底**：`I2C2_Init()` 会先测 P5.4/P5.5 能否推挽拉低、总线上有没有
器件应答；都不满足就改用 **P1.4/P1.5**；P1 上也没有器件应答则留在 P5 并如实
上报引脚状态。因此无论板子把 IIC2 布在哪一组，固件都能自己选对。

**实测确认的根因（2026-11-06 上板验证）**：**引脚组选错了**。
固件原先写死驱动 P5.4/P5.5，而这块板的 IIC2 器件实际接在 **P1.4/P1.5**；
再加上本片 P5.4/P5.5 根本推不动（`>PINX<` 证明），所以那条总线上一个
器件都不会应答，看起来就像"GPIO 没被驱动"。

修复方式不是改某个宏，而是让固件**上电自动选组**：先试 P5，拉不低或总线上
没有器件应答就切 P1.4/P1.5。切过去后 `[DIAG_1_3C_1_1_02]`，三个器件全部 ACK。

（顺带把 IIC2 从开漏改成准双向：开漏的"高"完全依赖上拉，内部上拉在 `P5PU`
里，万一没生效总线就永远上不去 —— 这条不是本次的元凶，但同样是坑，已一并改掉。）

验证顺序：

1. 串口助手发 `>DIAG<`，看第一个字段：
   * `[DIAG_0_...]` → 当前引脚组推挽也拉不低（P5.4 还是复位脚 / 未 bonding）。
   * `[DIAG_1_...]` → 引脚没问题，往下查器件与连线。
2. 发 `>PINX<` 一次问清引脚归属：
   `[PINX_<组>_<可驱动位图>_<P1M0>_<P1M1>_<P5M0>_<P5M1>_<P1>_<P5>_<P_SW2>]`
   * `<组>`：`0` = 正在用 P5.4/P5.5，`1` = 已切到 P1.4/P1.5；
   * 位图 bit0=P1.4 bit1=P1.5 bit2=P5.4 bit3=P5.5，`1` = 能拉低；
   * 后面几项是模式寄存器的**实际回读值**，用来判断写操作有没有生效
     （例如 P5M1 仍是 `3F` 说明复位默认值没被改掉）。
2. 发 `>PINS<`：SCL/SDA 会以 2 Hz 慢闪 3 秒。
   * 看得到闪 → 引脚受控，问题在器件侧（供电 / 上拉 / 焊接 / 地址）。
   * 完全不闪 → 同上，仍是引脚没受控。
3. 引脚受控但器件全无应答时，量三个点：
   * SCL/SDA 空闲是否被上拉到 VCC（模块上通常有 4.7K，缺了就补）；
   * 器件供电是否 3.3V（SSD1315 模块一般 3.3V，5V 可能不工作或损坏）；
   * 总线上是否有器件把 SDA 长期拉低（此时 `I2C2_Recover()` 会补 9 个时钟解开）。

代码层面已做的加固（本版）：

* IIC2 由**开漏**改为**准双向**输出 —— 开漏的"高"完全依赖上拉，内部上拉
  在 `P5PU`（xdata 扩展 SFR）里，一旦没生效，写 1 就等于悬空，看起来就像
  "GPIO 没被驱动"；准双向下写 1 一定有高电平。
* `Board_SwI2cPinsOk()` 修了一个会**把总线钉死在低电平**的 bug：它原来推挽
  拉低测完就直接切回开漏，而锁存器还停在 0，等于一直拉着 SCL/SDA 不放。
  现在会先把锁存器置 1 再恢复模式。

## 9. 阵列（8 片 24Cxx）只有一片应答时

`>SCAN<` 会把 `P_SW2.I2C_S` 的四种取值挨个扫一遍，输出四组：

```
[SCAN_02 0_02 0_00 0_02 1]
       │  │  │  │  │  │  │  └ I2C_S=3（P3.2/P3.3）上有 OLED → 说明这组其实是 IIC2 的脚
       │  │  │  │  │  │  └─── I2C_S=3 的阵列位图
       │  │  │  │  │  └────── I2C_S=2（P7.7/P7.6）
       │  │  │  │  └───────── I2C_S=1（P2.5/P2.4）
       │  │  │  └──────────── I2C_S=0（P1.5/P1.4）是否有 OLED
       │  │  └─────────────── I2C_S=0 的阵列位图
       │  └────────────────── ...
```

判读：

* 某一组的位图接近 **FF** → 8 片阵列就在那组引脚上，改 `CFG_I2C_S_SEL` 即可。
* 某组 `oN = 1`（看到 OLED）→ 该组引脚其实接的是 IIC2 的器件，
  说明这一路上**硬件 I2C 与软件 I2C 落在同一组脚**，需要把整条总线统一交给
  硬件 I2C（或统一交给软件 I2C），不能两套并行。
* 四组都是 `00` 且 `oN` 全 0 → 阵列的 SDA/SCL 根本没接到 MCU（查排线/供电）。
* 如果 `mN = 02` 且该组 `oN = 1` → 那 0x51 是 IIC2 上的 24C02，不是阵列芯片。

## 10. 排查：阵列能扫到、也能写，但读回全是 0

现象：`>DIAG<` 报 `[DIAG_1_3C_1_1_FF_3]`（8 片全 ACK、总线电平正常），
写入 `W_` 回 `[RX-OK]`，但 `INT_R` 读回全是 `00`，连**空白区也读到 `00`**
（正常应是 `FF`）。上位机初始化因此得到 `Chip health check 0/8`、
`Array capacity 0 B`。

**根因（本版已修）**：`EE_WriteBlock` 的事务组装缓冲写成了

```c
uint8_t tmp[4];                 /* ← 只够 2 字节地址 + 2 字节数据 */
...
for (i = 0; i < chunk; i++) tmp[n++] = buf[done + i];   /* chunk 最多 16 */
I2C1_Write(ee_sa(chipIdx), tmp, n);                     /* n 最多 18 */
```

一包 16 字节就要 18 字节缓冲，越界 14 字节，把栈上的 `done` / `i` / 型号
指针冲掉 —— 于是地址算错、数据写到别的页，事务本身却"成功"返回 `[RX-OK]`。

**为什么特别容易中招**：C51 的 SMALL 模式把局部数组放在 **128 字节的 data 区**，
越界不会像 x86 那样立刻崩，而是静默改掉相邻变量。这类 bug 只表现为
"数据不对"，不会报错。本工程的做法是：

> 任何"片内地址 + 数据包"的组装缓冲，一律 `static uint8_t xdata[]`，
> 尺寸按 `CFG_PKT_BYTES + 2` 留足，并在拷贝前把 `chunk` 夹到缓冲上限。

**后续自查清单**（改协议/改包长时必看）：

| 位置 | 缓冲 | 需要的尺寸 |
| --- | --- | --- |
| `EE_WriteBlock` | `s_ew[CFG_PKT_BYTES+2]` | 2 B 地址 + 16 B 数据 |
| `EE_ReadBlock` | `tmp[2]` | 只放地址，安全 |
| `M24_Write`（24C02） | `tmp[10]` | 1 B 地址 + 8 B 页，安全 |
| `Proto_SendR` | `s_row` 系 | 16 B |

改 `CFG_PKT_BYTES` 时必须同步检查 `s_ew` 与 `s_pkt`（`s_pkt` 已按宏定义）。

## 11. 读会话的握手：`>RX-OK<` 与 `[RX-OK]` 不能混用

读流程是"下位机推一包 → 上位机确认一包"，每包都要握手。这里有两个方向、
两种括号，搞混就会静默失败：

| 方向 | 格式 | 例 |
| --- | --- | --- |
| 上位机 → 下位机（命令、以及读会话里的确认） | `>…<` | `>INT_R<`、`>RX-OK<` |
| 下位机 → 上位机（应答、数据） | `[…]`、`>R_…<` | `[RX-OK]`、`>R_00,1A<` |

**症状**：写都成功，读只回来第一包 16 字节，然后下位机发 `[RX-ERR]` 提前结束；
上位机侧表现为芯片测试 `Chip health check 0/8`、`Array capacity 0 B`。

**原因**：上位机把确认发成了 `[RX-OK]`（方括号）。下位机的帧层只认 `>` 起始的帧，
于是整串 `[RX-OK]` 被当作帧外噪声丢弃，`Proto_Wait` 白等 `CFG_RXOK_TIMEOUT_MS`
（2000 ms）超时后退出读会话。

**修复（两侧都做了）**：

1. 上位机 `CapsaProtocol.WriteAck()` 改为发 `>{token}<`；
2. 下位机帧层同时接受 `[…]`（`Proto_OnByte` 里记 `s_close`），老上位机也能跑通，
   但**不要依赖**这条兼容路径 —— 新代码一律用 `>…<`。

用串口助手手工验证读流程时也要注意：收到 `>R_…<` 后必须回 `>RX-OK<`，
回 `[RX-OK]` 只能依赖固件的兼容分支。
